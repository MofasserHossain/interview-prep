# MongoDB Basics Interview Guide

MongoDB fundamentals: the document model, BSON types and `ObjectId`, inserting,
querying nested documents and arrays, projection, sorting and cursors, update and
array update operators, upserts, deletes, bulk writes, counting, basic indexes,
schema validation, embedding versus referencing, Mongoose versus the native
driver, and connecting from Node.js.

Every example runs in `mongosh` against MongoDB 8.2, and every output shown is
real. Each question starts from an empty database, and the blocks inside a
question run in order, each building on the last. The rest of the MongoDB
material builds on this guide: the Aggregation Pipeline guide covers every
pipeline stage, Indexing & Performance covers `explain` and index design, and
MongoDB Advanced covers replication, sharding, transactions, and schema patterns.

## 1. What Is MongoDB, And When Do You Choose It?

MongoDB is a document database. A record is a BSON document — binary JSON with
extra types such as `ObjectId`, `Date`, and `Decimal128`.

```js
{
  _id: ObjectId("65f1a2b3c4d5e6f7a8b9c0d1"),
  email: "a@b.com",
  profile: { name: "Mofasser", country: "BD" },
  roles: ["admin", "editor"],
  createdAt: ISODate("2026-01-15T10:00:00Z")
}
```

Choose it when:

- records are **self-contained aggregates** read as a unit — an order with its
  items, a post with its comments
- the shape varies per record, or evolves quickly
- you would otherwise join the same five tables on every read

Choose relational when:

- data has genuine many-to-many relationships queried from both directions
- you need multi-row transactions and database-enforced constraints as the
  normal case, not the exception
- reporting is ad hoc and you cannot predict the queries

Interview note:

"MongoDB scales better" is not a useful answer. A well-indexed relational database
handles far more load than most systems see, and MongoDB gains horizontal scaling
by making joins and cross-shard transactions the expensive exception rather than
the everyday tool. Name the tradeoff, not the trend.

Important:

Schemaless does not mean no schema. The schema lives in application code, where
the database cannot enforce it — and old documents keep their old shape forever.
Use schema validation (question 18) to get some of that back:

```js
db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["email", "createdAt"],
      properties: { email: { bsonType: "string", pattern: "^.+@.+$" } },
    },
  },
});
```

## 2. How Are Documents Stored, And Why Do BSON Types Matter?

The hierarchy is **database → collection → document**. Databases and collections
are created lazily, on the first insert.

| Rule | Detail |
| --- | --- |
| `_id` | required, unique in the collection, immutable; generated if omitted |
| Size | a document may not exceed **16MB** |
| Nesting | up to 100 levels of embedded documents |
| Field order | preserved as written |

BSON types you meet in interviews:

| Type | `$type` alias | Note |
| --- | --- | --- |
| Double | `"double"` | 64-bit float — the default for numbers with a fraction |
| 32-bit integer | `"int"` | what `mongosh` and the Node driver store for small whole numbers |
| 64-bit integer | `"long"` | `NumberLong()`, shown as `Long('...')` |
| Decimal128 | `"decimal"` | exact decimal — use for money |
| String | `"string"` | UTF-8 |
| Date | `"date"` | milliseconds since the epoch, always UTC |
| ObjectId | `"objectId"` | 12-byte id — question 3 |
| Object, Array, Boolean, Null | `"object"`, `"array"`, `"bool"`, `"null"` | |

Why it matters:

A query matches on **type as well as value**. The number `5` and the string `"5"`
are different values:

```js
db.items.insertMany([
  { _id: 1, sku: "KB", qty: 5 },
  { _id: 2, sku: "MS", qty: "5" },       // imported from a CSV as text
]);
db.items.find({ qty: 5 });
```

Output:

```txt
[
  { _id: 1, sku: 'KB', qty: 5 }
]
```

The string never matches, and range queries treat numbers and strings as
separate types, so `qty: { $gt: 1 }` skips it too. Find the bad documents by type:

```js
db.items.find({ qty: { $type: "string" } });
```

Output:

```txt
[
  { _id: 2, sku: 'MS', qty: '5' }
]
```

Interview trap:

Type drift is the most common "my query returns nothing" bug in MongoDB: ids
stored as strings in one collection and `ObjectId` in another, numbers arriving
as strings from forms or CSV files, dates stored as ISO strings. Validate types at
the boundary, and with a schema validator.

## 3. What Is An `ObjectId`?

A 12-byte identifier, generated by the **driver** — not the server — when you
insert a document without an `_id`.

```txt
65f1a2b3   c4d5e6f7a8   b9c0d1
└ 4-byte   └ 5-byte     └ 3-byte
  seconds    random,      counter
  since      per process
  the epoch
```

Because it starts with a timestamp, you can recover the creation time from it:

```js
db.aggregate([
  { $documents: [{ id: ObjectId("65f1a2b3c4d5e6f7a8b9c0d1") }] },
  { $project: { createdAt: { $toDate: "$id" } } },
]);
```

Output:

```txt
[
  { createdAt: ISODate('2024-03-13T12:57:23.000Z') }
]
```

Interview trap:

An `ObjectId` and its hex string are **different values**. An API receives ids as
strings, and passing one straight into a query silently finds nothing:

```js
db.users.insertOne({
  _id: ObjectId("65f1a2b3c4d5e6f7a8b9c0d1"),
  name: "Alice",
});
db.users.findOne({ _id: "65f1a2b3c4d5e6f7a8b9c0d1" });
```

Output:

```txt
null
```

```js
db.users.findOne({ _id: ObjectId("65f1a2b3c4d5e6f7a8b9c0d1") });
```

Output:

```txt
{ _id: ObjectId('65f1a2b3c4d5e6f7a8b9c0d1'), name: 'Alice' }
```

In Node, convert with `new ObjectId(id)` after checking `ObjectId.isValid(id)`,
and return a 400 for a malformed id rather than a 500.

Important:

- Sorting by `_id` is **roughly** insertion order — only to the second, and not
  across machines whose clocks disagree. Use an explicit `createdAt` when order
  matters.
- An `ObjectId` is not a secret. It reveals creation time and is partly
  predictable, so never use it as an access token.
- Any unique value can be `_id`: an email, a natural key, or a UUID.

## 4. How Do You Insert Documents, And What Does `ordered` Change?

`insertOne` and `insertMany` return the inserted ids. `insertMany` is **ordered**
by default: it stops at the first error.

```js
db.users.insertMany([
  { _id: 1, name: "Alice" },
  { _id: 1, name: "Duplicate" },       // fails: _id 1 already exists
  { _id: 2, name: "Bob" },
]);
```

Output:

```txt
MongoBulkWriteError: E11000 duplicate key error collection: test.users index: _id_ dup key: { _id: 1 }
```

```js
db.users.find();
```

Output:

```txt
[
  { _id: 1, name: 'Alice' }
]
```

Bob was never attempted. With `ordered: false`, MongoDB tries every document and
reports all the failures at the end. The insert still reports the duplicate, but
Bob gets in:

```js
db.users.drop();
db.users.insertMany(
  [
    { _id: 1, name: "Alice" },
    { _id: 1, name: "Duplicate" },
    { _id: 2, name: "Bob" },
  ],
  { ordered: false },
);
db.users.find();
```

Output:

```txt
[
  { _id: 1, name: 'Alice' },
  { _id: 2, name: 'Bob' }
]
```

When to use it:

- **ordered** (default) when later documents depend on earlier ones
- **unordered** for bulk imports and backfills — faster, because the server can
  apply writes in parallel, and one bad row does not abandon the rest

Interview note:

Even ordered, `insertMany` is **not a transaction**. Alice stayed inserted after
the failure. If a batch must be all-or-nothing, use a transaction — covered in
MongoDB Advanced.

## 5. What Is The Difference Between `find()` And `findOne()`?

| | `find()` | `findOne()` |
| --- | --- | --- |
| Returns | a **cursor** | a single document or `null` |
| Documents | many | one |
| Chainable | `.sort()`, `.limit()`, `.skip()` | no |
| Empty result | an empty cursor | `null` |

```js
const cursor = db.users.find({ country: "BD" }); // lazy, nothing fetched yet
const users = await cursor.toArray(); // now it executes

// one document or null
const user = await db.users.findOne({ email: "a@b.com" });
```

`find()` is **lazy** — it returns a cursor and fetches in batches as you iterate.
That matters for large result sets: iterating streams batches rather than loading
everything into memory.

```js
for await (const user of db.users.find({ active: true })) {
  await process(user); // constant memory
}
```

Interview trap:

`findOne()` still scans until it finds a match. On an unindexed field it reads the
whole collection just to return one document — it is not inherently cheap.

`findOne(query)` is equivalent to `find(query).limit(1)` and is implemented that
way.

## 6. Which Query Operators Should You Know?

```js
db.users.insertMany([
  { _id: 1, name: "Alice", age: 34,
    country: "BD", plan: "pro" },
  { _id: 2, name: "Bob",   age: 27,
    country: "US", plan: "free" },
  { _id: 3, name: "Carol", age: 41,
    country: "BD", plan: "free", deletedAt: ISODate("2026-02-01T00:00:00Z") },
  { _id: 4, name: "Dan",   age: 19,
    country: "IN" },                  // no plan field
]);
```

Several conditions in one filter are an implicit **AND**:

```js
db.users.find({ country: "BD", age: { $gte: 30 } }, { name: 1 });
```

Output:

```txt
[
  { _id: 1, name: 'Alice' },
  { _id: 3, name: 'Carol' }
]
```

`$or` takes an array of complete conditions:

```js
db.users.find({ $or: [{ plan: "pro" }, { age: { $lt: 20 } }] }, { name: 1 });
```

Output:

```txt
[
  { _id: 1, name: 'Alice' },
  { _id: 4, name: 'Dan' }
]
```

Interview trap:

`$ne` and `$nin` also match documents where the field is **missing**. "Users not
on the pro plan" includes Dan, who has no plan at all:

```js
db.users.find({ plan: { $ne: "pro" } }, { name: 1, plan: 1 });
```

Output:

```txt
[
  { _id: 2, name: 'Bob', plan: 'free' },
  { _id: 3, name: 'Carol', plan: 'free' },
  { _id: 4, name: 'Dan' }
]
```

Add `plan: { $exists: true, $ne: "pro" }` when missing should not count.

`$exists` and `null` — `{ deletedAt: null }` matches **both** a null value and a
missing field; `$exists: false` matches only missing:

```js
db.users.find({ deletedAt: { $exists: false } }, { name: 1 });
```

Output:

```txt
[
  { _id: 1, name: 'Alice' },
  { _id: 2, name: 'Bob' },
  { _id: 4, name: 'Dan' }
]
```

| Group | Operators |
| --- | --- |
| Comparison | `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin` |
| Logical | `$and`, `$or`, `$nor`, `$not` |
| Element | `$exists`, `$type` |
| Evaluation | `$regex`, `$expr`, `$mod`, `$text`, `$jsonSchema` |
| Array | `$all`, `$elemMatch`, `$size` |

When to use it:

- `$in` rather than `$or` when every branch tests the **same** field —
  `{ country: { $in: ["BD", "IN"] } }` is simpler and optimizes better
- an explicit `$and` only when two conditions use the same operator on the same
  field, since a JavaScript object cannot hold duplicate keys
- `$regex` anchored with `^` and case-sensitive when you want an index to help;
  `/abc/i` has to examine every index key

## 7. How Do You Query Nested Documents And Arrays?

```js
db.products.insertMany([
  { _id: 1, name: "Laptop", specs: { ram: 16, cpu: "M3" },
    tags: ["tech", "sale"],
    ratings: [ { user: "a", score: 5 }, { user: "b", score: 2 } ] },
  { _id: 2, name: "Phone",  specs: { cpu: "A17", ram: 8 },
    tags: ["tech"],
    ratings: [ { user: "c", score: 4 } ] },
  { _id: 3, name: "Desk",   specs: { ram: null },
    tags: ["home", "sale"],
    ratings: [ { user: "a", score: 3 }, { user: "d", score: 5 } ] },
]);
```

Dot notation reaches into embedded documents:

```js
db.products.find({ "specs.ram": { $gte: 8 } }, { name: 1 });
```

Output:

```txt
[
  { _id: 1, name: 'Laptop' },
  { _id: 2, name: 'Phone' }
]
```

Interview trap:

Matching a **whole embedded document** is an exact, **order-sensitive**
comparison. Phone stores `{ cpu, ram }`, so asking for `{ ram, cpu }` finds nothing:

```js
db.products.find({ specs: { ram: 8, cpu: "A17" } }, { name: 1 });
```

Output:

```txt
[]
```

Use dot notation for each field instead — `{ "specs.ram": 8, "specs.cpu": "A17" }`.

A value tested against an array matches if **any element** matches:

```js
db.products.find({ tags: "sale" }, { name: 1 });
```

Output:

```txt
[
  { _id: 1, name: 'Laptop' },
  { _id: 3, name: 'Desk' }
]
```

`$all` requires every listed value, and `$size` matches an exact length:

```js
db.products.find({ tags: { $all: ["tech", "sale"] } }, { name: 1 });
```

Output:

```txt
[
  { _id: 1, name: 'Laptop' }
]
```

Interview trap:

Two conditions on an array of documents may be satisfied by **different
elements**. "Products user `a` rated 4 or higher" wrongly includes Desk — `a`
gave it 3, but user `d` gave it 5:

```js
db.products.find(
  { "ratings.user": "a", "ratings.score": { $gte: 4 } },
  { name: 1 },
);
```

Output:

```txt
[
  { _id: 1, name: 'Laptop' },
  { _id: 3, name: 'Desk' }
]
```

`$elemMatch` requires **one element** to satisfy both conditions:

```js
db.products.find(
  { ratings: { $elemMatch: { user: "a", score: { $gte: 4 } } } },
  { name: 1 },
);
```

Output:

```txt
[
  { _id: 1, name: 'Laptop' }
]
```

The same trap applies to ranges on an array of numbers:
`{ scores: { $gt: 5, $lt: 10 } }` matches `[1, 20]`, because `20 > 5` and `1 < 10`.
Use `{ scores: { $elemMatch: { $gt: 5, $lt: 10 } } }`.

## 8. How Does Projection Work?

The second argument to `find` chooses the fields to return. Returning less means
less network traffic, less memory, and — with the right index — no document fetch
at all.

```js
db.posts.insertOne({
  _id: 1,
  title: "Hello",
  body: "A long body...",
  author: { name: "Alice", email: "alice@example.com" },
  comments: [
    { by: "Bob",   text: "Nice" },
    { by: "Carol", text: "Thanks" },
    { by: "Dan",   text: "+1" },
  ],
});
db.posts.find({}, { title: 1, "author.name": 1, comments: { $slice: -2 } });
```

Output:

```txt
[
  {
    _id: 1,
    title: 'Hello',
    author: { name: 'Alice' },
    comments: [ { by: 'Carol', text: 'Thanks' }, { by: 'Dan', text: '+1' } ]
  }
]
```

The positional `$` returns only the **first array element that matched** the
query:

```js
db.posts.find({ "comments.by": "Carol" }, { title: 1, "comments.$": 1 });
```

Output:

```txt
[
  {
    _id: 1,
    title: 'Hello',
    comments: [ { by: 'Carol', text: 'Thanks' } ]
  }
]
```

| Projection | Effect |
| --- | --- |
| `{ title: 1 }` | include `title` (and `_id`) |
| `{ body: 0 }` | exclude `body`, keep the rest |
| `{ _id: 0, title: 1 }` | the only allowed mix of include and exclude |
| `{ "author.name": 1 }` | one nested field |
| `{ comments: { $slice: -2 } }` | last two array elements |
| `{ "comments.$": 1 }` | first element matching the query |
| `{ comments: { $elemMatch: { by: "Carol" } } }` | first element matching this condition |

## 9. How Do Sorting, Limiting, And Cursors Work?

```js
db.tasks.insertMany([
  { _id: 1, title: "A", priority: 2 },
  { _id: 2, title: "B" },                     // no priority
  { _id: 3, title: "C", priority: 1 },
  { _id: 4, title: "D", priority: null },
]);
db.tasks.find({}, { _id: 0 }).sort({ priority: 1, _id: 1 });
```

Output:

```txt
[
  { title: 'B' },
  { title: 'D', priority: null },
  { title: 'C', priority: 1 },
  { title: 'A', priority: 2 }
]
```

Missing and `null` sort **first** in ascending order and last in descending
order, and compare equal to each other — so `_id` breaks their tie. That is the
opposite of PostgreSQL, which puts nulls last in ascending order by default.

When a field holds different types, MongoDB sorts by type first:

```txt
MinKey < null < numbers < strings < objects < arrays < BinData
       < ObjectId < booleans < dates < timestamps < regex < MaxKey
```

Cursors:

- `find()` returns a cursor; documents arrive in **batches** as you iterate
- an idle cursor is closed by the server after **10 minutes**; a slow consumer
  loop gets `CursorNotFound`
- `toArray()` loads every result into memory — fine for 50 documents, a crash for
  5 million; iterate with `for await` instead
- `limit()` belongs in the query, not in application code: with an index that
  matches the sort, the server stops after N entries

Important:

A sort on a non-unique field returns ties in no defined order, so paging with
`skip` can repeat or drop documents between pages. End every sort used for paging
with a unique field such as `_id`.

## 10. Which Update Operators Should You Know?

```js
db.products.insertOne({
  _id: 1, name: "Keyboard", price: 50, stock: 10, views: 0, legacyCode: "KB-1",
});
db.products.updateOne(
  { _id: 1 },
  {
    $set: { price: 45, "meta.onSale": true },     // creates meta if missing
    $inc: { stock: -2, views: 1 },
    $unset: { legacyCode: "" },
    $max: { highestPrice: 50 },                   // only raises the value
    $currentDate: { updatedAt: true },
  },
);
db.products.findOne({ _id: 1 }, { updatedAt: 0 });
```

Output:

```txt
{
  _id: 1,
  name: 'Keyboard',
  price: 45,
  stock: 8,
  views: 1,
  highestPrice: 50,
  meta: { onSale: true }
}
```

New fields are added in lexicographic order of their names (since 5.0), which is
why `highestPrice` lands before `meta`.

The update result distinguishes **matched** from **modified**. Setting a field to
the value it already has matches without modifying:

```js
// price is already 45
db.products.updateOne({ _id: 1 }, { $set: { price: 45 } });
```

Output:

```txt
{
  acknowledged: true,
  insertedId: null,
  matchedCount: 1,
  modifiedCount: 0,
  upsertedCount: 0
}
```

Interview trap:

An update without operators is a **replacement** — and `updateOne` refuses one,
because that is almost always a bug:

```js
db.products.updateOne({ _id: 1 }, { price: 40 });
```

Output:

```txt
MongoInvalidArgumentError: Update document requires atomic operators
```

`replaceOne` does it deliberately, and every field not in the new document is gone:

```js
db.products.replaceOne({ _id: 1 }, { price: 40 });
db.products.findOne({ _id: 1 });
```

Output:

```txt
{ _id: 1, price: 40 }
```

| Operator | Does |
| --- | --- |
| `$set` / `$unset` | set or remove a field; dot paths create nested documents |
| `$inc` / `$mul` | add to or multiply a number, atomically |
| `$min` / `$max` | update only if the new value is lower / higher |
| `$rename` | rename a field |
| `$currentDate` | set the server's current date |
| `$setOnInsert` | set only when an upsert inserts — question 12 |

Why it matters:

`$inc: { stock: -2 }` is applied atomically on the server. Reading `stock` in the
application, subtracting, and writing it back loses updates when two requests
race — the same lost-update problem as in SQL.

## 11. How Do You Update Elements Inside An Array?

```js
db.carts.insertOne({
  _id: 1,
  items: [ { sku: "KB", qty: 1 }, { sku: "MS", qty: 2 } ],
  tags: ["new"],
});
db.carts.updateOne(
  { _id: 1 },
  {
    $push: { items: { sku: "PEN", qty: 5 } },
    $addToSet: { tags: { $each: ["new", "promo"] } },
  },
);
// items.$ is the first element the query matched
db.carts.updateOne(
  { _id: 1, "items.sku": "MS" },
  { $inc: { "items.$.qty": 3 } },
);
db.carts.findOne({ _id: 1 });
```

Output:

```txt
{
  _id: 1,
  items: [
    { sku: 'KB', qty: 1 },
    { sku: 'MS', qty: 5 },
    { sku: 'PEN', qty: 5 }
  ],
  tags: [ 'new', 'promo' ]
}
```

`$addToSet` skipped the duplicate `"new"`; `items.$` updated only the element the
query matched.

Continuing with the same cart:

```js
// every element
db.carts.updateOne({ _id: 1 }, { $mul: { "items.$[].qty": 2 } });
// every element matching the filter
db.carts.updateOne(
  { _id: 1 },
  { $set: { "items.$[big].bulk": true } },
  { arrayFilters: [{ "big.qty": { $gte: 10 } }] },
);
db.carts.updateOne({ _id: 1 }, { $pull: { items: { sku: "KB" } } });
// append two tags, keep the last 3
db.carts.updateOne(
  { _id: 1 },
  { $push: { tags: { $each: ["sale", "hot"], $slice: -3 } } },
);
db.carts.findOne({ _id: 1 });
```

Output:

```txt
{
  _id: 1,
  items: [
    { sku: 'MS', qty: 10, bulk: true },
    { sku: 'PEN', qty: 10, bulk: true }
  ],
  tags: [ 'promo', 'sale', 'hot' ]
}
```

| Operator | Affects |
| --- | --- |
| `$push` | appends; with `$each`, `$sort`, and `$slice` it keeps a capped, sorted array |
| `$addToSet` | appends only if an identical element is absent |
| `$pull` / `$pullAll` | removes elements matching a condition / listed values |
| `$pop` | removes the first (`-1`) or last (`1`) element |
| `items.$` | the **first** element matched by the query |
| `items.$[]` | **every** element |
| `items.$[name]` + `arrayFilters` | every element matching the filter |

Interview trap:

`$addToSet` on documents compares the **whole document, field order included**.
`{ sku: "KB", qty: 1 }` and `{ qty: 1, sku: "KB" }` are different elements, so it
will happily add a "duplicate".

Important:

`$push` with `$slice` is the standard fix for an unbounded array: keep the last
50 events on the parent document and write the full history to its own
collection.

## 12. What Is An Upsert, And When Do You Use `findOneAndUpdate`?

An **upsert** updates the matching document, or inserts one if none matches.
`$setOnInsert` supplies fields that should only be written on insert.

```js
db.users.updateOne(
  { email: "alice@example.com" },
  {
    $set: { lastLoginAt: ISODate("2026-03-01T10:00:00Z") },
    $setOnInsert: { plan: "free", createdAt: ISODate("2026-03-01T10:00:00Z") },
  },
  { upsert: true },
);
db.users.updateOne(
  { email: "alice@example.com" },
  {
    $set: { lastLoginAt: ISODate("2026-03-09T08:30:00Z") },
    $setOnInsert: { plan: "free", createdAt: ISODate("2026-03-09T08:30:00Z") },
  },
  { upsert: true },
);
db.users.find({}, { _id: 0 });
```

Output:

```txt
[
  {
    email: 'alice@example.com',
    createdAt: ISODate('2026-03-01T10:00:00.000Z'),
    lastLoginAt: ISODate('2026-03-09T08:30:00.000Z'),
    plan: 'free'
  }
]
```

The first call inserted — note that `email` came from the **query**. The second
matched, so only `lastLoginAt` changed and `createdAt` kept its original value.

`findOneAndUpdate` updates and **returns the document** in one atomic step. The
classic use is a sequence number:

```js
db.counters.findOneAndUpdate(
  { _id: "invoice" },
  { $inc: { seq: 1 } },
  { upsert: true, returnDocument: "after" },
);
db.counters.findOneAndUpdate(
  { _id: "invoice" },
  { $inc: { seq: 1 } },
  { upsert: true, returnDocument: "after" },
);
```

Output:

```txt
{ _id: 'invoice', seq: 2 }
```

Without `returnDocument: "after"` you get the document **before** the update.

Important:

Two concurrent upserts with the same filter can both decide "no match" and both
insert. Put a **unique index** on the filter field, so the loser fails with a
duplicate-key error instead of creating a duplicate. Since 4.2 the server
retries that case itself when the filter is an equality match on the unique
index's fields.

Use cases:

- "create or update" from a sync job or a webhook
- counters and sequences
- claiming a job: `findOneAndUpdate({ status: "queued" }, { $set: { status: "running" } })`
  hands each job to exactly one worker

## 13. How Do You Delete Documents, And What Are TTL Indexes For?

```js
db.sessions.insertMany([
  { _id: 1, user: "alice", expiresAt: ISODate("2026-03-01T00:00:00Z") },
  { _id: 2, user: "bob",   expiresAt: ISODate("2026-03-20T00:00:00Z") },
  { _id: 3, user: "carol", expiresAt: ISODate("2026-02-10T00:00:00Z") },
]);
db.sessions.deleteMany({ expiresAt: { $lt: ISODate("2026-03-15T00:00:00Z") } });
```

Output:

```txt
{ acknowledged: true, deletedCount: 2 }
```

| Method | Removes |
| --- | --- |
| `deleteOne(filter)` | the first matching document |
| `deleteMany(filter)` | every matching document |
| `findOneAndDelete(filter)` | one document, and returns it — a queue pop |
| `drop()` | the whole collection, **including its indexes**, instantly |

A **TTL index** deletes expired documents automatically:

```js
db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });
```

`expireAfterSeconds: 0` means "delete when `expiresAt` is in the past"; a value of
`3600` with a `createdAt` field means "one hour after creation".

Important:

- The TTL monitor runs about **every 60 seconds**, so documents outlive their
  expiry briefly. Filter on `expiresAt` in queries that must never see expired
  data.
- A TTL index works on a single `Date` field (or an array of dates). A string date
  never expires.
- `deleteMany({})` removes documents one at a time and keeps the indexes;
  `drop()` is far faster when you want everything gone.

When not to use it:

Deleting data the business may need later. A soft delete — a `deletedAt` field
plus a partial index on live documents — keeps history and makes restores
trivial.

## 14. What Is `bulkWrite`, And When Is It Worth Using?

`bulkWrite` sends a batch of mixed inserts, updates, replaces, and deletes in
**one round trip**.

```js
db.products.insertMany([ { _id: 1, stock: 5 }, { _id: 2, stock: 0 } ]);
db.products.bulkWrite([
  { insertOne: { document: { _id: 3, stock: 7 } } },
  { updateOne: { filter: { _id: 1 }, update: { $inc: { stock: -1 } } } },
  { deleteOne: { filter: { _id: 2 } } },
  {
    replaceOne: { filter: { _id: 4 }, replacement: { stock: 1 }, upsert: true },
  },
]);
```

Output:

```txt
{
  acknowledged: true,
  insertedCount: 1,
  insertedIds: { '0': 3 },
  matchedCount: 1,
  modifiedCount: 1,
  deletedCount: 1,
  upsertedCount: 1,
  upsertedIds: { '3': 4 }
}
```

`insertedIds` and `upsertedIds` are keyed by the operation's position in the
array — the upsert was operation `3`.

```js
db.products.find();
```

Output:

```txt
[
  { _id: 1, stock: 4 },
  { _id: 3, stock: 7 },
  { _id: 4, stock: 1 }
]
```

Why it matters:

Ten thousand `updateOne` calls are ten thousand network round trips. One
`bulkWrite` of ten thousand operations is a handful — the driver splits it into
batches automatically.

When to use it:

- syncing a batch of records from another system
- migrations and backfills
- applying a queue of changes collected by a worker

Interview note:

Bulk writes are ordered by default, like `insertMany`; pass `{ ordered: false }`
for independent operations. Either way a bulk write is **not atomic** — a failure part-way leaves the
earlier operations applied. MongoDB 8.0 also added a client-level `bulkWrite`
that spans several collections in one request.

## 15. `countDocuments` vs `estimatedDocumentCount`

| | `countDocuments(filter)` | `estimatedDocumentCount()` |
| --- | --- | --- |
| Accepts a filter | yes | no |
| How | runs an aggregation over matching documents | reads collection metadata |
| Cost | a scan of what matches — an index scan if the filter is indexed | constant |
| Accuracy | exact | can drift after an unclean shutdown, or with orphaned documents on a sharded cluster |

```js
db.orders.countDocuments({ status: "paid" }); // exact, uses an index on status
db.orders.estimatedDocumentCount(); // instant "about how many"
```

When to use it:

- `countDocuments` for business logic — "does this user have unpaid invoices?"
- `estimatedDocumentCount` for dashboards and admin screens showing collection
  size

Interview trap:

`countDocuments({})` on a 200-million-document collection is a full scan. A UI
that shows "Page 1 of 4,213,902" on every request pays that cost each time — show
"more results" instead, or cache the count.

The old `count()` is deprecated: without a filter it silently returned the
metadata estimate, which is how the two methods came to be split.

## 16. What Are Indexes, At A Basic Level?

An index is a sorted structure of field values that points to documents, so a
query can jump to matches instead of scanning every document. Every collection has
a unique index on `_id`.

```js
db.users.insertMany([
  { _id: 1, email: "alice@example.com", country: "BD" },
  { _id: 2, email: "bob@example.com",   country: "US" },
]);
db.users.createIndex({ email: 1 }, { unique: true });
db.users.createIndex({ country: 1, createdAt: -1 });
db.users.getIndexes();
```

Output:

```txt
[
  { v: 2, key: { _id: 1 }, name: '_id_' },
  { v: 2, key: { email: 1 }, name: 'email_1', unique: true },
  {
    v: 2,
    key: { country: 1, createdAt: -1 },
    name: 'country_1_createdAt_-1'
  }
]
```

A unique index is also a **constraint**:

```js
db.users.insertOne({ _id: 3, email: "alice@example.com" });
```

Output:

```txt
MongoServerError: E11000 duplicate key error collection: test.users index: email_1 dup key: { email: "alice@example.com" }
```

The basics to state in an interview:

- index the fields you **filter and sort** on, in queries that run often
- a compound index serves queries on its **leftmost prefix** — `{ country,
  createdAt }` helps `country` alone, not `createdAt` alone
- every index slows writes and uses RAM
- check with `explain("executionStats")`: `IXSCAN` good, `COLLSCAN` a full scan

Study path:

Index types, the ESR rule, covered queries, `explain` output, and slow-query
diagnosis are covered in depth in the MongoDB Indexing & Performance guide.

## 17. Embedding vs Referencing: How Do You Model Relationships?

```js
// Embedded - one document
{
  _id: ObjectId("..."),
  title: "My Post",
  comments: [
    { author: "A", text: "Nice", createdAt: ISODate("...") },
    { author: "B", text: "Thanks", createdAt: ISODate("...") }
  ]
}
```

```js
// Referenced - two collections
{ _id: ObjectId("p1"), title: "My Post" }
{ _id: ObjectId("c1"), postId: ObjectId("p1"), author: "A", text: "Nice" }
```

| Embed when | Reference when |
| --- | --- |
| Read together, always | Queried independently |
| Bounded growth | **Unbounded** growth |
| Updated together | Updated at different rates |
| Child has no identity of its own | Child is a real entity |

The decisive question is **growth**. A document has a hard **16MB limit**, and an
unbounded array is the most common way to hit it.

The extended reference pattern is the usual compromise — duplicate the few fields
you display, reference the rest:

```js
{
  _id: ObjectId("o1"),
  userId: ObjectId("u1"),
  userName: "Mofasser",     // duplicated for display
  userEmail: "a@b.com",     // avoids a $lookup on every order read
  items: [...]
}
```

Tradeoff:

Duplication removes the join and adds a consistency burden — when a user renames
themselves, you need a plan for the copies. For an order, the name **at time of
purchase** is arguably the correct value anyway, which is the same reasoning as
storing price on an order line in SQL.

Interview method:

Design from the **access patterns**, not the entities. List the screens and API
calls, note which data each reads and writes together and how often, then shape
documents so the hottest reads are a single document fetch. The rest of the
modeling patterns — bucket, subset, computed, outlier — are in MongoDB Advanced.

## 18. How Does Schema Validation Work?

A validator makes the server reject documents that do not match a schema —
enforcement that application code alone cannot guarantee once several services
write to the same collection.

```js
db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["customerId", "total", "status"],
      properties: {
        customerId: { bsonType: "string" },
        total: { bsonType: ["decimal", "double", "int"], minimum: 0 },
        status: { enum: ["pending", "paid", "shipped", "cancelled"] },
      },
    },
  },
  validationLevel: "strict",
  validationAction: "error",
});
db.orders.insertOne({ customerId: "c1", total: -5, status: "lost" });
```

Output:

```txt
MongoServerError: Document failed validation
```

The error also carries a `details` object (`errInfo` in the driver) naming every
rule that failed:

```txt
details: {
  operatorName: '$jsonSchema',
  schemaRulesNotSatisfied: [
    {
      operatorName: 'properties',
      propertiesNotSatisfied: [
        { propertyName: 'total',
          details: [ { operatorName: 'minimum', reason: 'comparison failed', consideredValue: -5 } ] },
        { propertyName: 'status',
          details: [ { operatorName: 'enum', reason: 'value was not found in enum', consideredValue: 'lost' } ] }
      ]
    }
  ]
}
```

Log it. Without the details, "Document failed validation" says nothing about
which field is wrong.

| Setting | Options |
| --- | --- |
| `validationLevel` | `"strict"` — every insert and update; `"moderate"` — only documents that are already valid |
| `validationAction` | `"error"` — reject; `"warn"` — accept and log |

Adding a validator to an existing collection:

```js
db.runCommand({
  collMod: "orders",
  validator: { $jsonSchema: { bsonType: "object", required: ["status"] } },
  validationLevel: "moderate",
});
```

Important:

A validator is **not applied retroactively**. Existing invalid documents stay
until they are next updated. Roll out with `"warn"` or `"moderate"` first, find
the violators with `db.orders.find({ $nor: [{ $jsonSchema: schema }] })`, fix
them, then switch to `"strict"` and `"error"`.

## 19. Mongoose vs The Native Driver: Which Should You Use?

The **native driver** (`mongodb`) is a thin client: you send queries and get plain
objects back. **Mongoose** is an ODM on top of it that adds schemas, casting,
validation, middleware, and `populate`.

```js
// Native driver
const orders = db.collection("orders");
const recent = await orders
  .find({ customerId, status: "paid" })
  .sort({ createdAt: -1 })
  .limit(10)
  .toArray();
```

```js
// Mongoose
const orderSchema = new mongoose.Schema(
  {
    customerId: {
      type: mongoose.Types.ObjectId,
      ref: "Customer",
      required: true,
    },
    status: {
      type: String,
      enum: ["pending", "paid", "shipped"],
      default: "pending",
    },
    total: { type: Number, min: 0 },
  },
  { timestamps: true },
);

const Order = mongoose.model("Order", orderSchema);

const recent = await Order.find({ customerId, status: "paid" })
  .sort({ createdAt: -1 })
  .limit(10)
  .lean(); // plain objects, skips document hydration
```

| | Native driver | Mongoose |
| --- | --- | --- |
| Schema and validation | server validator or your own code | built in, in the application |
| Casting | none — `"42"` stays a string | casts to the schema type |
| Hooks | none | `pre`/`post` middleware |
| Relations | `$lookup` or manual queries | `populate()` |
| Overhead | minimal | hydration, casting, change tracking |
| TypeScript | generics on `Collection<T>` | inferred from the schema |

Interview trap:

`populate()` is **not a join**. It runs a second query with `$in` for each
populated path, so populating in a loop is an N+1, and populating a large array
fetches every referenced document. Use `$lookup` in an aggregation when the join
is heavy.

When to use it:

- Mongoose for a CRUD-heavy application where schema, defaults, and validation in
  one place save real code
- the native driver for performance-critical services, heavy aggregation, or
  when you already validate at the edge with something like Zod
- either way, call `.lean()` on Mongoose reads that only return JSON — hydration
  is the largest part of its overhead

## 20. How Do You Connect MongoDB From Node.js Properly?

```js
import { MongoClient } from "mongodb";

const client = new MongoClient(process.env.MONGODB_URI, {
  maxPoolSize: 10,
  minPoolSize: 2,
  serverSelectionTimeoutMS: 5000,
  retryWrites: true,
});

let connected;

export async function getDb() {
  connected ??= client.connect();
  await connected;
  return client.db();
}
```

Important:

Create **one** client for the process and reuse it. The driver maintains its own
connection pool internally — calling `MongoClient.connect()` per request exhausts
connections and is the most common MongoDB performance bug in Node.

In a serverless function, create the client at **module scope**: the module stays
loaded between warm invocations, so the pool is reused. Keep `maxPoolSize` small
there — every concurrent function instance opens its own pool.

In development, hot reload re-evaluates modules and would create a new client on
every edit. Cache it on `globalThis` in that case:

```ts
const globalForMongo = globalThis as typeof globalThis & {
  _mongo?: MongoClient;
};
const client = globalForMongo._mongo ?? new MongoClient(uri);
if (process.env.NODE_ENV !== "production") globalForMongo._mongo = client;
```

`retryWrites: true` — the default in current drivers — lets the driver retry a
write once after a failover, which makes an election largely invisible to the
application. `retryReads` does the same for reads.

## 21. What Are The Common MongoDB Beginner Gotchas?

**Type mismatches** — `5` vs `"5"`, `ObjectId` vs its hex string. Both silently
match nothing.

**Dates stored as strings** — they compare as text and cannot use date operators.
Store `Date`.

**`$ne` and `$nin` match missing fields** — add `$exists: true` when that is wrong.

**Two array conditions without `$elemMatch`** — they can match different elements.

**Whole-document equality on an embedded document** — order-sensitive; use dot
notation.

**`updateOne` without operators** — rejected; `replaceOne` wipes every other field.

**Positional `$` updates only the first match** — use `$[]` or `arrayFilters`.

**Read-modify-write in the application** — use `$inc`, `$push`, and conditional
updates so the server applies the change atomically.

**`toArray()` on a huge result** — iterate the cursor instead.

**Unbounded arrays** — the 16MB document limit is real; cap with `$push` +
`$slice` or use a separate collection.

**No unique index behind an upsert** — concurrent upserts create duplicates.

**A new `MongoClient` per request** — the driver already pools; this exhausts
connections.

Strong answer:

> I model documents around how the application reads them: data read together is
> embedded, unbounded or independently queried data is referenced, and a few
> display fields are duplicated when that saves a join on every read. On the query
> side I watch for type drift, use dot notation and `$elemMatch` deliberately, and
> make writes atomic with update operators rather than read-modify-write. I back
> the important invariants with unique indexes and a schema validator, because
> "schemaless" only moves the schema into code that the database cannot enforce.
